IMPORTANT CONSTRAINTS (READ BEFORE STARTING)
-------------------------------------------------
- Do NOT install, run, or require any database server locally on the
  developer's machine. Use MongoDB Atlas (cloud) exclusively — no
  local MongoDB installation, no Docker container running a database
  for development or testing.
- Do NOT use any local file storage. Use Cloudinary (cloud) exclusively
  for every attachment/file upload — no local disk fallback, no
  storing files in a local `uploads/` folder even temporarily.
- Brevo must be used strictly via its transactional HTTP API with an
  API key (`BREVO_API_KEY`) — never SMTP credentials, never a local
  mail server, never PHPMailer-over-SMTP. Every email (verification,
  password reset, reminders) goes through Brevo's HTTP API only.
- Standard Composer dependencies required to run the app itself
  (`mongodb/mongodb`, `cloudinary/cloudinary_php`, `vlucas/phpdotenv`,
  `firebase/php-jwt`) are fine — the app needs these to function. Do
  not introduce anything beyond what's strictly required to run the
  PHP application (no local dev databases, no bulky extra tooling, no
  large datasets to download).
- ONE UNAVOIDABLE TECHNICAL NOTE: connecting to MongoDB from PHP
  requires the `mongodb` PHP extension (installed via PECL) to be
  present in whatever environment actually RUNS the PHP code — this
  is a runtime requirement of the language/driver, not a "local
  database install." On Render, use a Docker-based PHP environment
  where the `mongodb` extension is installed inside the Dockerfile
  (in the deployment environment, not on your personal machine). If
  you need to run/test the PHP app itself somewhere, prefer doing so
  in a cloud dev environment/container (e.g. within Codex/OpenCode's
  own execution environment, or directly on Render) rather than
  installing PHP + the mongodb extension on your own machine.

MASTER PROMPT (paste this in)
========================================================================

You are building "CloudTasks" — a cloud-based to-do list web
application for a Nigerian polytechnic HND final year project. Users
register, create and manage tasks across devices with cloud
persistence, deadline reminders, prioritization, and progress
tracking. Follow this spec exactly, and follow the IMPORTANT
CONSTRAINTS above without exception. Build incrementally, one module
at a time, confirming each works before moving to the next.

PROJECT GOAL
-------------
A reliable, accessible task management platform that replaces paper
notes and offline apps — data lives centrally in the cloud so it's
available, backed up, and synchronized across any device the user logs
into, with authentication, prioritization, deadline reminders, and
progress tracking.

TECH STACK (use exactly this)
-------------------------------
  - PHP 8.2 (procedural or lightweight MVC structure)
  - MongoDB Atlas (cloud-hosted database, via the `mongodb/mongodb`
    Composer library) — NOT PostgreSQL/MySQL, NOT a local database
  - HTML5, CSS3, Vanilla JavaScript (no Bootstrap, no frontend
    framework)
  - Cloudinary for all file attachments (cloud storage + on-the-fly
    thumbnail transformations) — NOT local disk, NOT Supabase Storage
  - Brevo transactional HTTP API (cURL/axios POST with `BREVO_API_KEY`)
    for email verification, password reset, and deadline reminder
    emails — NOT SMTP, since Render blocks SMTP ports anyway and this
    project must not touch a local mail setup
  - Deployment: Render (Docker-based PHP web service, so the `mongodb`
    extension can be installed in the image) + a Render Cron Job (or
    an external trigger like cron-job.org hitting a protected
    endpoint) for scheduled deadline-reminder checks
  - Database hosting: MongoDB Atlas (cloud only)

FOLDER STRUCTURE

DATABASE COLLECTIONS (MongoDB documents)
--------------------------------------------
users
  _id, name, email (unique index), passwordHash,
  isEmailVerified: bool,
  timezone: string (e.g. "Africa/Lagos" default — deadline reminders
    must fire at the RIGHT local time, not server UTC time),
  themePreference: "light"|"dark",
  createdAt, updatedAt, deletedAt (soft-delete for account closure)

taskLists   (categories/projects — e.g. "Work", "Personal", "School")
  _id, userId, name, color, position, createdAt, updatedAt

tasks
  _id, userId, taskListId (nullable = "Uncategorized"),
  title, description,
  priority: "low"|"medium"|"high",
  status: "pending"|"in_progress"|"completed",
  dueAt: Date (store in UTC, convert using the user's timezone on
    display AND when scheduling reminders),
  completedAt: Date|null,
  isRecurring: bool, recurrenceRule: "daily"|"weekly"|"monthly"|null,
  recurrenceParentId: ObjectId|null (links generated recurring
    instances back to the original task),
  position: number (for manual drag-reorder within a list),
  subtasks: [
    { _id, title, isCompleted: bool, position }
  ]   // embedded array — MongoDB's document model means subtasks
       // don't need a separate collection/join; fetched with the
       // task in one query
  attachments: [
    { url, publicId, fileName, fileSize, uploadedAt }
  ]   // Cloudinary secure_url + public_id per file, embedded directly
       // on the task document
  createdAt, updatedAt, deletedAt (soft-delete/trash bin)

reminderLogs   (kept as its OWN collection, not embedded, so cron
                 dedup queries stay fast and simple)
  _id, taskId, sentAt, reminderType: "24h_before"|"1h_before"|
  "overdue", status: "sent"|"failed"
  // prevents duplicate reminder emails being sent twice for the same
  // task/threshold if the cron job runs more often than the reminder
  // window, or overlaps a prior run

sessions (if not using pure JWT — lets you support "log out of all
  devices")
  _id, userId, tokenHash, createdAt, expiresAt, userAgent, ipAddress

Indexes to create in MongoDB Atlas:
  - users.email (unique)
  - tasks: compound index on (userId, dueAt) for fast smart-view
    queries (Today/Upcoming/Overdue)
  - tasks: compound index on (userId, taskListId)
  - reminderLogs: compound index on (taskId, reminderType) for fast
    dedup checks during the cron run

CORE FEATURES — COVER EVERY SCENARIO BELOW
----------------------------------------------

1. AUTHENTICATION
   - Register/login, bcrypt/argon2 password hashing
   - Email verification via Brevo's API before full account access (or
     at minimum before reminder emails are sent to that address)
   - Password reset flow with a single-use, time-limited token
   - Session handling via secure httpOnly cookies or JWT — either is
     fine, but document your choice in Chapter 3; support "log out of
     all devices" via the sessions collection if you choose that route
   - Rate limiting on login/register/password-reset endpoints
   - CSRF protection on all state-changing form submissions

2. TASK LISTS / CATEGORIES
   - Create/rename/delete/reorder custom lists (Work, Personal, etc.)
   - Deleting a list must NOT silently delete its tasks — either
     require the list to be empty first, or reassign its tasks to
     "Uncategorized" (choose one, document the choice)

3. TASK CRUD — THE CORE FEATURE
   - Create/edit/delete tasks with title, description, priority, due
     date+time, list assignment
   - Soft delete: deleted tasks go to a "Trash" view with a restore
     option for a configurable window (e.g. 30 days) before permanent
     removal
   - Mark complete/incomplete (toggle), with `completedAt` recorded for
     progress-tracking analytics
   - Subtasks/checklist items embedded on the task document, each
     independently toggleable, parent task showing an "X of Y done"
     count
   - Drag-and-drop or up/down reordering within a list (position
     field), implemented in vanilla JS (no framework)
   - Optional file attachment per task via Cloudinary — enforce a file
     size/type limit server-side, not just in the frontend `accept`
     attribute; upload happens through a signed server-side Cloudinary
     call (never expose your Cloudinary API secret in frontend JS)

4. RECURRING TASKS (explicit scenario handling)
   - A task can be marked recurring (daily/weekly/monthly)
   - When a recurring task is marked complete, the system generates
     the NEXT occurrence automatically (a new task document linked via
     `recurrenceParentId`) rather than mutating the same document —
     this preserves history so progress-tracking stats aren't
     corrupted
   - Deleting a recurring task should ask: "delete just this occurrence
     or the whole recurring series?" — handle both paths explicitly
   - Editing a recurring task's due time/priority should ask whether
     the change applies to future occurrences only or this one alone

5. PRIORITIZATION & ORGANIZATION
   - Priority levels (low/medium/high) with clear visual distinction
   - Filter/sort by: priority, due date, status, list, creation date
   - Search across task titles/descriptions
   - "Today", "Upcoming", "Overdue", "Completed" smart views computed
     from dueAt/status rather than manually maintained flags
   - Overdue tasks (dueAt in the past AND status != completed)
     visually highlighted distinctly across every view

6. DEADLINE REMINDERS (the "cloud-based" differentiator worth
   detailing carefully)
   - A scheduled job (Render Cron Job, or an external trigger hitting
     a protected `/cron/send-reminders` endpoint every 15 minutes)
     scans for tasks whose dueAt falls within upcoming reminder windows
     (e.g. 24 hours before, 1 hour before) AND haven't already had that
     reminder logged in reminderLogs for this task+type
   - Convert dueAt (stored UTC) to the task owner's stored timezone
     BEFORE deciding whether a reminder threshold has been crossed
   - Send the reminder via Brevo's transactional HTTP API using
     BREVO_API_KEY, then log it in reminderLogs immediately so a cron
     overlap or retry never sends a duplicate email
   - Also send an "overdue" digest-style reminder — batch a user's
     overdue tasks into a single digest email per run, not one email
     per overdue task
   - In-app notification/badge for upcoming and overdue tasks,
     independent of the email reminder

7. PROGRESS TRACKING
   - Per-list completion percentage (completed tasks / total tasks in
     that list, excluding trashed tasks)
   - Overall dashboard: tasks completed today/this week, current
     streak of days with at least one task completed, overdue count,
     upcoming count
   - Simple chart (plain HTML/CSS bars, or a lightweight approach) of
     completions over the last 7/30 days

8. MULTI-DEVICE SYNC (explicit design note for your Chapter 3)
   - Because all data lives centrally in MongoDB Atlas rather than in
     browser local storage, "sync across devices" is inherent to the
     architecture — logging in from any device shows the same data
   - For a near-real-time feel across multiple open tabs/devices
     without full WebSocket infrastructure, implement periodic
     polling (e.g. re-fetch the task list every 20-30 seconds, or on
     window focus) — document this as a deliberate, pragmatic choice
     rather than claiming true push-based real-time sync
   - Use `updatedAt` timestamps for simple last-write-wins conflict
     resolution if the same task is edited from two devices near-
     simultaneously; document this limitation honestly

9. DATA EXPORT / BACKUP (answers the abstract's "backup" claim
   concretely)
   - "Export my tasks" button -> download a JSON or CSV snapshot of
     all the user's tasks/lists — a tangible backup artifact and an
     easy, demonstrable feature for your defense

10. RESPONSIVE UI
    - Mobile-first CSS (flexbox/grid, media queries) — no framework
    - Test at common breakpoints (mobile ~375px, tablet ~768px,
      desktop ~1200px+)
    - Touch-friendly controls for mobile

EDGE CASES TO EXPLICITLY HANDLE
------------------------------------
  - User sets a due date in the past -> either warn before saving or
    accept it and immediately show it as overdue; pick one and be
    consistent
  - User changes their timezone setting after tasks already exist ->
    dueAt values (stored UTC) don't change, but DISPLAYED local time
    and reminder-scheduling calculations must immediately reflect the
    new timezone on next render/cron run
  - Deleting a task list that still has active (non-trashed) tasks ->
    handled per section 2 above (reassign or block), never silent
    cascade-delete
  - Restoring a task from Trash whose parent list was deleted in the
    meantime -> reassign to "Uncategorized" rather than erroring
  - A recurring task's series is deleted while an instance is
    mid-cycle -> clarify in the confirmation dialog exactly which
    documents are affected before committing
  - Cron job runs twice for the same window (overlap/retry) ->
    reminderLogs prevents duplicate sends
  - User has zero tasks (brand-new account) -> friendly empty states
    on every view
  - Very long task titles/descriptions -> truncate with "show more" in
    list views
  - Bulk operations (select multiple tasks -> mark complete/delete) ->
    confirm before a bulk permanent action, make bulk soft-delete (to
    Trash) the default, not bulk permanent delete
  - Session/token expiry mid-edit -> fail gracefully with a clear
    "please log in again" message rather than silently discarding
    unsaved changes
  - Cloudinary upload failure (network error, size limit exceeded) ->
    clear retry option, task itself still saves even if the attachment
    step fails
  - Deleting a task or account: remove the associated Cloudinary
    assets (via the Admin API `destroy` call using each attachment's
    `publicId`) rather than leaving orphaned files accumulating in
    your Cloudinary account
